## Hypothesis

The ingestion service account is reading documents that no human user in the requesting business unit can read — quietly bringing restricted content into the retrievable index.

## Why this matters

This is the floor of every RAG authorization problem. If the ingestion identity has broader access than the population of users who will query the resulting index, the index becomes a flat copy of restricted content with the access controls stripped off.

## Data sources

- Source-system audit logs (SharePoint / Drive / Confluence / Notion / Jira / Slack / Box / S3)
- RAG ingestion job logs (job ID, document IDs, target index)
- IdP group membership and ACL data for the consuming application

## Detection logic

See Paper 3 §RAG-001 for full pseudocode + Sigma. Summary: for each ingestion job in the window, compare the union of users authorized to read each ingested document against the population that can query the target index. Flag every document where the consumer set is not a subset of the source-side reader set, weighted by classification.

## Evidence to capture

- Ingestion job ID, target index, ingestion identity
- Document IDs ingested
- Source classification labels
- ACL diff between source readers and consumers
